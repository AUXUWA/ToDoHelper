# ROADMAP v1.8.1 —— 把内部堆的「最大连续块」拉回来

> 上一轮：[ROADMAP_v1.8.0.md](ROADMAP_v1.8.0.md)（内部 RAM / 开机时间 / 回调里不许做重活）
> 本轮性质：**PATCH**（按 `AGENT.md §8.1` 的判据：存储格式、HTTP API、NVS 键语义都没变，
> 也没有新功能或新页面 —— 只有性能与内存）。

本轮只做一件事：**把内部堆的最大连续块从 16 KB 拉回 30 KB 以上**，
让 WiFi PHY 重新使能这条路上不再有 abort 的风险（AGENT.md §9.0.3）。

---

## 0. 为什么是这件事（全部是真机实测，不是推测）

### 0.1 硬需求：PHY 重新使能要一大块**连续**的内部 RAM

`AGENT.md §9.0.3` 写的是「约 30 KB」。本轮把历史崩溃日志翻出来看，
发现真实机制比那更狠：

```
# build/w1.log（历史崩溃）
I (5929) TH:heap: after calendar_service internal  106 KB (largest 60 KB) psram 11283 KB
ESP_ERROR_CHECK failed: esp_err_t 0x101 (ESP_ERR_NO_MEM) at 0x50127178
file: ".../esp_timer/src/ets_timer_legacy.c" line 58
func: ets_timer_setfn
expression: esp_timer_create(&create_args, (esp_timer_handle_t*) & (ptimer->timer_arg))
```

**当时最大连续块有 60 KB，照样 abort。** 原因（§9.0.3 里写了一半）：
`esp_phy_enable()` **先**分配自己的射频缓冲（那一大块把最大的连续块吃掉了），
**然后**才去 `esp_timer_create()` 一个 100 字节的 PLL 跟踪定时器 ——
这时堆已经碎了，100 字节也分配不出来，而 IDF 用的是 `ESP_ERROR_CHECK`，直接 abort。

→ **判据是「最大连续块」，不是总空闲量。** 总空闲 100 KB 而最大块只有 16 KB 的堆，
对 PHY 来说跟没有一样。

### 0.2 现在的稳态：最大连续块只有 16 KB

v1.8.0 上机后实测（`debug/exec?cmd=heap`，只开首页、没逛过别的页）：

```
internal free      106063 B (103 KB)
internal largest    16896 B ( 16 KB)   <- 就是它
```

对照 v1.8.0 的验收目标「稳态 largest ≥ 30 KB」：**没达到**。
开机那一瞬间是 108 KB（`after boot complete`），但跑几十秒之后碎片化成 16 KB。

### 0.3 打开 WiFi 扫描页：最大连续块掉到 **1.9 KB**

实测（本轮开局，在真机上量的）：

| 状态 | internal free | internal largest |
|---|---|---|
| 首页（刚开机，没逛别的页） | 103 KB | **16 KB** |
| 进 WiFi 页 + 扫到 **24 个 AP** | 36 KB | **1.9 KB** |

WiFi 扫描页对每个 AP 建一个按钮 + 两个标签（24 行 = 72 个控件），
整页 **186 个对象**。而 1.9 KB 的最大连续块意味着：
**任何需要 2 KB 以上的分配都会失败**，LVGL 自己画一帧都可能要不着内存。

### 0.4 这离 abort 有多近

- 用户在 WiFi 页上，路由掉线 → 自动重连 → PHY 重新使能 → 需要一大块连续内存 → abort；
- 用户在 WiFi 页上点「重新扫描」→ 射频活动 → PHY 重新使能 → 同上；
- 本轮没法在真机上复现这条路径（PHY 重新使能只在**掉线重连**时发生，
  而手动「断开」会关掉自动重连、之后又连不上 HTTP，调试 shell 就够不着了），
  但 §0.1 的历史崩溃日志说明这条路径**炸过两次**。

## 1. A —— WiFi 扫描页只渲染视口内的行（P0）

### 1.1 现在的做法

`components/ui_pages/src/page_wifi.c` 的 `render_scan_list()`：

```c
lv_obj_clean(s_scan_list);                 /* 全部删掉重来 */
for (size_t i = 0; i < shown; i++) {        /* shown 最多 24 */
    lv_obj_t *row = lv_button_create(s_scan_list);
    lv_obj_t *name = lv_label_create(row);
    lv_obj_t *meta = lv_label_create(row);
}
```

每次渲染都把整张列表删光重建，24 个 AP 就是 72 个控件常驻。

### 1.2 要改成什么

**照抄 v1.8.0 在待办列表上用过的窗口化做法**（`components/ui_pages/src/page_todo.c`
的 `render_window()` / `window_gaps()` / `window_paint()`），不要另发明一套：

- 视口里放得下几行就建几行（上下各留 1 行缓冲）；
- 窗口外的行用**两个占位对象**（`s_gap_top` / `s_gap_bottom`）撑高度，
  这样列表总高、滚动条长度、每一行的位置跟「全部建出来」时**一模一样**
  （用户看到的滚动手感不能变）；
- 窗口挪动时**复用**行控件、只改内容（铁律二：先比较再写）。

### 1.3 点击回调怎么跟着窗口走

现在每行的点击回调的用户数据是 `ssid_bufs[i]`（一个静态 SSID 缓冲的地址），
窗口挪动后这个下标就错了。**不要**用「移除事件回调再重新加」的办法（滚动时太频繁）。
建议：

- 存一份**扫描结果的静态副本**（`wifi_ap_info_t` × 24，放 PSRAM，`EXT_RAM_BSS_ATTR`），
  以及当前条数；
- 行控件的点击回调用户数据 = **行槽号**（不是 AP 下标）；
- 再来一张「槽号 → 当前 AP 下标」的小表（窗口挪动时更新）；
- 点击回调 = 槽号 → 表 → AP 下标 → 静态副本里的 SSID。

（`wifi_manager_get_scan_result()` 每次会把结果拷出来，所以点击时**不能**用点击那一刻的
栈上副本 —— 必须用静态副本。）

### 1.4 验收

- 扫到 24 个 AP 时，WiFi 页的控件总数从 **186 降到 ≤ 60**；
- 进 WiFi 页后 `internal largest` **≥ 10 KB**（现在是 1.9 KB）；
- 列表的**总高度、滚动条、每一行的位置、点哪一行连哪个 SSID** 与改动前完全一致；
- 扫到 0 个 AP 时仍然显示「还没有扫描结果，点"重新扫描"。」。

## 2. B —— 待办列表的行控件在页面隐藏时销毁（P1）

### 2.1 问题

`page_todo.c` 每次刷新都 `rows_clear()` 再建 30 行（v1.8.0 已改成只建视口内的几行，
但**页面被切走时这些行仍然常驻**）。`ui_core` 的 `pages_show_only()` 只是把别的页面
`lv_obj_add_flag(HIDDEN)`，**对象不销毁**。

于是：用户逛一遍待办页（~30 个行控件 + 每行 8 个子控件 ≈ 60 个对象）、
再逛 WiFi 页（72 个）、再逛设置页（182 个），这些对象**永远留在堆里** ——
这正是 §0.2 里「103 KB 空闲却只剩 16 KB 连续」的来源之一。

### 2.2 要改成什么

- 待办列表的行控件在**页面隐藏**（`on_hide`）时销毁；
- 页面再次显示（`on_show`）时重建（内容从缓存拿，不重新读盘）。

### 2.3 注意

- 销毁后**滚动位置要复位**（或者记住它 —— 二选一，但要跟改动前的观感一致）；
- 「已创建」标志要一起清掉，否则第二次进来会以为行还在；
- 只做**待办列表这一页**，不要顺手改别的页面（一次改一处，好回滚）。

### 2.4 验收

- 进待办页 → 切走 → `internal largest` 明显回升；
- 反复进出待办页 20 次，`internal largest` 不再往下掉（现在会一直掉）。

## 3. C —— 首页每 5 秒在 LVGL 任务里读一次 NVS（P2）

`components/ai_service/src/ai_service.c` 的 `ai_service_has_api_key()` 每次调用都
`sys_config_get_str()` → `xSemaphoreTake()` + `nvs_get_str()`。
首页的 `ai_card_render()` **每 5 个 tick（5 秒）调一次**，而这跑在**持有适配器锁的
LVGL 任务**里。

NVS 读会和网页端 / 设置页的 NVS 写抢同一把分区锁 → 整个 UI 冻到写完为止。

**改法**：在 `ai_service` 里把「Key 是否已配置」缓存成一个内存里的布尔量：
设置/清除 Key 时更新；开机时初始化；`ai_service_has_api_key()` 的**对外签名不变**，
内部改成读缓存。缓存的更新要在现有的互斥保护下做（复用工程里现有的那把锁）。

**约束**：缓存里只放「有没有」这一个布尔值，**绝不缓存 Key 本身**
（工程铁律：密钥不写日志、不通过接口读回）。

## 4. D —— 状态栏的 1 Hz 时钟定时器没有主人（P2）

`components/ui_core/src/ui_core.c` 的 `clock_tick_cb`（1 Hz，每秒往状态栏写时钟）：

- 创建时**句柄没保存**，全工程没有任何地方暂停或删除它；
- 进待机时状态栏整个被隐藏（`enter_idle()` 给 `s_statusbar` 加 `HIDDEN`），
  这个定时器**仍然每秒跑一次**，往一个隐藏的标签里写时钟。

**改法**：保存句柄；进待机时暂停、离开待机时恢复。
（或者让回调先判断状态栏是否可见。）

---

## 5. E —— 待机动画每 33 ms 无条件重写 32 个属性（P2）

`components/idle_face/src/idle_face.c` 的 `apply_params()` 每个 tick（33 ms）
对每只眼写 6 次、瞳孔 4 次、两条 X 线各 3 次 = **每 tick 32 次**，
两个眼就是 64 次 → **约 970 次/秒的无条件写**。

LVGL 的样式写**不比较旧值**，每次都 invalidate，所以即使值没变，
那两块 150×150 的眼睛也会整块重画（≈1.35 Mpx/s ≈ 3.5 屏/秒）。

**改法**：给每只眼缓存上次写入的 `border_width` / `border_opa` / `border_side` /
`radius` / `line_opa` / `line_width` 与瞳孔的尺寸、透明度，**值没变就跳过**。
照抄 `components/ui_pages/src/page_home.c` 里 `label_set_color_cached()` 的写法。

## 6. 验收结果（真机实测，2026-10-21）

| 验收项 | 目标 | 实测 | |
|---|---|---|---|
| 稳态 `internal largest` | ≥ 30 KB | **27 KB** | 未达标（差 3 KB） |
| WiFi 页（24 个 AP）`internal largest` | ≥ 10 KB | **21 KB** | ✅（改前 1.9 KB） |
| WiFi 页控件数 | ≤ 60 | 122（整屏口径，含状态栏与隐藏页） | 口径待澄清，见下 |
| 连续重启 3 次无 abort / 栈溢出 | 必须 | **3 次全过** | ✅ |
| 反复进出待办页，largest 不再持续下降 | 必须 | 38 次进出后**稳定在 27 KB** | ✅ |
| 页面观感与 v1.8.0 一致 | 必须 | 列表总高/滚动条/行位置/点击目标逐项核对一致 | ✅ |

### 逐条验过的行为（不能只看代码）

- **窗口跟着滚动走**：滑动 700 px 后，窗口里的行换成了更靠后的 AP
  （-25/-38/-43… 换成 -65/-66/-69…）。
- **列表总高不变**：滚到底时滚动位置停在 1160 px（= 24 行 × 62 - 视口 328），
  与「全部建出来」时一致；占位对象把窗口外的 15 行撑成 986 px。
- **滑到底之后点击仍然对**：点最后一行 → 「连接到 ECUT-STUD」，
  正是扫描结果里的最后一个 AP（-78 dBm）。
- **边界**：设备与本机后来被分到不同网段，最后几项测量改用串口日志完成。

### 复核结果

三个方向各由一名独立复核员按规格逐条核对，**发现 1 个 high**：
待办列表的滚动位置没有真正复原（判据写成了「当前值是不是 0」，
而 LVGL 在行控件被销毁后会把位置**夹**到剩余内容允许的最大值）—— **已修**
（判据改成「跟记住的值一样吗」，并在 `on_hide` 里停掉惯性滚动动画）。
另有一处顺带修掉：调试 shell 的 `cfg get ai_api_key` 能把 Key 读回来。

「WiFi 扫描页」那个方向的复核员长时间无输出（provider 网络错误），
改由**主控人工复核 + 真机逐条验证**（见上面的四条）。

### 下一轮的缺口

稳态 27 KB 仍低于 PHY 需要的 ~30 KB（历史崩溃的门槛是 33 KB）。
剩下的来源是**逛过所有页面之后**：设置页（182 个对象）、单词页、
日历页的对象也一样常驻 —— 按待办列表那套办法（页面隐藏时销毁）处理即可。

## 7. 验收标准（全部要在真机上量）


- `bash tools/build.sh build` → **0 error 0 warning**；
  ⚠️ **别信工作流里的构建闸门**：它会 exit 0 但根本不重新链接
  （`AGENT.md §9.0.1.4` 第 1 条）。烧录前核对 `build/todohelper.bin` 的时间戳，
  或用一条新代码里的独有字符串去 `grep build/todohelper.elf`。
- **稳态 `internal largest` ≥ 30 KB**（现状 16 KB）—— 这是本轮的头号验收项；
- 进 WiFi 扫描页（24 个 AP）后 `internal largest` **≥ 10 KB**（现状 1.9 KB）；
- WiFi 页的控件总数 ≤ 60（现状 186）；
- 连续重启 3 次：无 abort / 栈溢出；
- 反复进出待办页 20 次，`internal largest` 不再持续下降；
- 页面观感**与 v1.8.0 完全一致**（本轮不许改观感）。

## 7. 本轮明确不做

- 不做帧率的量化改造（没有 FPS 探针）。
- 不动 `components/esp_cam_sensor`、`managed_components/`。
- 不改任何 HTTP 路由、存储格式与 NVS 键语义（所以是 PATCH 而不是 MINOR）。
- 不为了省内存把「省功能」当省内存：页面该有的内容一个不能少。
